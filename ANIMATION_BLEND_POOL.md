# Fixed animation blend pool: opt-in read-only pressure monitor

This standalone D3D9Proxy change diagnoses one remaining limit on native Helm's
Deep + static Isengard level loading. It does **not** expand the pool, load a
second world, import assets, or modify collision/Havok. It samples the
retail x86 animation **blend slot** allocator's next-free index.

## Verified reconstructed layout

The source oracle is `Vespucci/Engine/Magellan/MgAgBlendEval.inc`,
`FUN_0045549c / Mg_0045549c_BlendSlotAlloc`. The relevant layout is:

- Root: pointer stored at `0x00CD7E7C`.
- Arena: pointer at `root + 0x0C`.
- Slot array: `arena + 0x9004`.
- Element stride: `0xF8` (248 bytes).
- Stock capacity: `0x400` (1024 slots).
- Next-free counter: `slot_base + 0x3E000` (1024 × 248).
- Instruction at `0x004554B1`: `81 FE 00 04 00 00` (`CMP ESI, 0x400`).

The counter lives **immediately after** the original array. Changing that
single CMP to 4096 without relocating/rewriting the owning object would
overwrite unrelated memory. `memorypatch.cpp` Patch 29 remains OFF.

**Different pools:** do not confuse this array with the animation **event**
pool near `0x00CD9970` or the 512-entry **clip/skeleton binding cache**.

## Opt in

On a disposable copy of Conquest with the matching standalone x86 proxy DLL,
add to `proxy.ini` beside the game executable:

```ini
[StaticMapPools]
Monitor=1
BlendMonitor=1
```

New auto-generated `proxy.ini` files include `BlendMonitor=0` by default.
Existing files are **not overwritten**, so add the key manually if needed.
The option can also run with `Monitor=0`, using the same existing pinned
worker thread; a new thread is NOT created. The worker checks 4 times/sec,
but the blend CSV is logged at most once per second, including before level
construction and when no D3D frame is presented.

Output: `animation_blend_pool.csv` in the game's EXE folder, with
`time_ms,root_ptr,arena_ptr,slot_base,counter_ptr,slot_stride,retail_capacity,next_free_index,peak_next_free_index,guard_limit,valid,status`.

- `OK`: counter within expected stock bounds.
- `NEAR_CAP`: >=1008 and <1024.
- `AT_CAP`: 1024, the stock boundary.
- `UNVERIFIED_GUARD`: changed/unreadable allocator guard; do NOT trust a count.
- `NO_ROOT`, `NO_ARENA`, `BAD_RANGE`, `UNREADABLE`, `RACED`,
  `OUT_OF_RANGE`: invalid sample, not proof of exhaustion.

Each sample reads the known x86 guard fingerprint, validates readable memory
using `VirtualQuery`, reads the counter under exception guards, and
rechecks root/arena pointers to reject some teardown races. It never
writes to game objects or patches the EXE. It is still a sampled observation,
not an atomic snapshot: **next-free index is NOT live blend object count**.
Peak resets when the arena pointer changes. Logs append across launches.

If `Monitor=1`, the existing offline analyzer can incorporate this CSV:

```powershell
python tools/analyze_runtime_pressure.py --game-dir "C:\Games\LOTR Conquest" --json
```

The analyzer requires the VA CSV generated by `Monitor=1`; if using only
`BlendMonitor=1`, inspect the blend CSV directly.

## Validation contract

CI checks synthetic CSV interpretations, read-only invariants, and an
MSVC x86 compile/link of the complete standalone proxy. That does NOT
prove actual runtime behavior. Compare untouched Helm's Deep, untouched
Isengard, then a disposable merged native PAK/BIN. If loading fails while
blend use remains low, inspect PAK/BIN references, shape/MOPP/Havok,
materials/occlusion and VA fragmentation before blaming this pool.

**Release gate:** no increase above 1024 until the owning arena's whole
allocation/layout, every consumer and teardown path are mapped and a real
game stress test demonstrates correctness.
